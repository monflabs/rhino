# Optimizations tried and dropped

The experiments of [OPTIMIZATION.md](OPTIMIZATION.md) that measured no gain, or a regression elsewhere, and were not
kept, with what was measured and why it did not work, so that they are not tried again without a new reason. Each row
gives the date of the experiment where it is known.

## Test context

These results hold for the machine and the JVM they were measured on. The JIT decides most of them: what C2 inlines
depends on the size of the code it has already compiled (`InlineSmallCode`), on per-method budgets
(`DesiredMethodLimit`, `LiveNodeCountInliningCutoff`), on the order in which methods get hot, on the intrinsics, the GC
barriers and the instruction set. **Another JVM can give different results**: another vendor or build (for example a
non-HotSpot JIT such as OpenJ9 or the Graal compiler), another JDK version, another GC, another CPU architecture
(the size of the compiled code, which the thresholds are compared with, differs), or non-default JIT flags. A dropped experiment may be worth
retesting there, and a kept optimization may not hold there.

Context of the experiments from 2026-11-03 on:

| | |
|---|---|
| Machine | Apple M2 (8 cores: 4 performance, 4 efficiency), 24 GB, macOS 27.2 |
| JDK | Azul Zulu 25.36+15-CA, OpenJDK 25.0.4+7-LTS, HotSpot 64-Bit Server VM, tiered C1/C2, G1, default flags |
| Harnesses | the perf gate (`buildtools/perf-gate.sh`, [benchmarks/README.md](benchmarks/README.md)); JavascriptPerformance (Octane, SunSpider), compiled, `--warmup=1 --iterations=1`, both language versions in one JVM (`VERSION_ECMASCRIPT` first, then `VERSION_ES6`), the two jars alternating, one JVM per run, medians of wall time |

The earlier rows were measured on the development machine before the context was recorded; the JDK used is not
known for them.

## Findings about the JIT

- **A compilation race decides `deltablue` under `VERSION_ECMASCRIPT`** (2026-11-03). Run as the first engine of its
  JVM, it takes either about 25 s or about 31 s, on the same jar. The cause is `PropertyCache.getPropAndThis`: when it
  gets a standalone C2 compile before the script methods that call it, its size, which depends on the profile at that
  moment (one more slot class seen by `keyMatches`), is either 2.9 KB or 3.4 KB, around `InlineSmallCode`; above it,
  C2 refuses to inline it into the script methods ("already compiled into a big method", 170 to 200 times), and every
  access pays a call and a heap-allocated `LookupResult`. Forcing it inline
  (`-XX:CompileCommand=inline,org.monflabs.mozilla.javascript.PropertyCache::getPropAndThis`) made all 6 runs fast
  (24.3–25.6 s against 30.8–31.4 s). An A/B of a change on `deltablue` under `VERSION_ECMASCRIPT` therefore mostly
  measures which side of the race each run fell on: look at the individual runs, not only the median.
- **Inlining the cache everywhere is not free either.** Below `InlineSmallCode`, the hit path (about 2.4 KB of
  compiled code per site) is inlined at every cached site, and in large script methods such as `box2d`'s it uses up
  the per-method budgets, so that other calls stop being inlined (rows of 2026-11-03 below). The same mechanism made
  `crypto-sha1` 55% slower with `-XX:InlineSmallCode=8000` (the `GlobalNameCache` row). A hit path that does not
  depend on these thresholds has to be much smaller: a map check and a field load, as shared shapes would give.
- **How to see it**: `-XX:+UnlockDiagnosticVMOptions -XX:+LogCompilation` (one XML element per compile, with its
  inlining decisions and code size; `-XX:+PrintInlining` interleaves the compiler threads), and the count of
  `inline_fail` reasons per callee between a fast and a slow run.
